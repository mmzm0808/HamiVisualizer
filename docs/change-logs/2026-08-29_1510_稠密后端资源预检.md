# 稠密后端资源预检

- 时间：2026-08-29 15:10（+08:00）
- 范围：`hamivisualizer/model/hamiltonian.py`、`hamivisualizer/tests/test_hardening.py`、`tools/render_ui_regression.py`。
- 背景：上一轮放开了 `NX/NY` 的模型输入范围，以便能带研究不被小屏幕渲染上限阻挡；但当前建阵与本征态后端仍使用稠密矩阵。极大尺寸若直接进入 NumPy 分配，可能导致系统换页、界面无响应甚至进程崩溃。

## 问题定位

`NX/NY` 的持久化上限是模型安全校验，不等于当前机器可以实际计算的规模。此前 `HamiltonianBuilder` 会先枚举 OBC 全部活动元胞、构造索引，再分配 `Nat×Nat` 稠密矩阵；半无限模式也会先建立 ribbon 基。对 `100000×100000` 这类合法、可保存但当前后端不可计算的研究输入，缺少明确的前置反馈。

## 实施修改

1. 增加 `estimate_dense_working_set_bytes(nat, boundary_kind)`：按复数稠密矩阵和常见临时/本征向量缓冲给出偏保守的工作集估计。
2. 增加 256 MiB 的计算安全预算 `DENSE_WORKING_SET_LIMIT_BYTES`，仅用于运行时预检：
   - 半无限在构建 ribbon 前检查 `lattice.N × NY`；
   - OBC 在枚举 `active_cells()` 前检查完整 `lattice.N × NX × NY` 上界，避免为了判断不可计算而先分配巨大元胞列表；随后对实际掩膜后的活动集合再检查一次。
3. 超预算时抛出可读的 `ValueError`，由现有控制器转为红色错误提示和过期状态；提示包含估算 MiB、安全预算、减小 NX/NY 或等待稀疏后端的建议，并明确“模型仍可保存，输入范围没有被限制”。
4. 新增单元测试覆盖：估算值、半无限与 OBC 大尺寸均在矩阵分配前拒绝；没有创建大数组或枚举百万级元胞。
5. 离屏工具新增 `--dense-guard-demo`，在 100%/150% 浅色/深色下验证超大输入仍可编辑、错误位置清楚且布局不溢出。
6. 在 `README-v0.3.md` 的性能说明中记录当前稠密后端预检与“可保存、不限制输入”的用户可见语义，避免把运行时保护误解成模型格式限制。

## 影响、风险与后续

- 收益：大尺寸能带/模型输入不再因渲染限制被禁止，但当前稠密后端会在资源明显不足时安全失败，避免“点了计算后卡死”。
- 兼容性：不改 `MAX_NX/MAX_NY`、模型 JSON、矩阵公式、边界语义或现有小/中型模型；没有破坏性 API 变更，新增函数可供后续稀疏后端复用或替换。
- 取舍：当前预算是保守保护而非硬件精确内存探测；不同机器可用内存不同，因此提示建议仍以稀疏后端为长期解决方案。形状掩膜的上界预检可能比实际活动元胞数更保守，但避免了高成本枚举，且不影响保存和编辑。
- 成功标准：保护发生在任何大规模 `active_cells`/矩阵分配之前；错误可恢复、输入可继续修改；全量回归无新增失败，100%/150% 双主题画面无裁切。
